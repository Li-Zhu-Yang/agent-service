# 架构说明

## 1. 总体结构

系统为单体 FastAPI 应用，按模块分层：接口层 → Agent 引擎 → RAG 引擎 → 基础设施 → 数据层。

```
┌─────────────────────────────────────────────┐
│  前端（原生 JS 聊天页 / 运营后台）           │
└───────────────┬─────────────────────────────┘
                │ SSE / REST
┌───────────────▼─────────────────────────────┐
│  api/  接口层                               │
│  chat(SSE) / conversations / knowledge /    │
│  admin / auth                               │
└───────┬──────────────────┬──────────────────┘
        │                  │
┌───────▼───────┐  ┌───────▼───────────────┐
│  agent/       │  │  rag/                │
│  LangGraph 工作流│  │  入库 + 混合检索      │
│  意图→检索→工具→回复│  │  解析/分块/向量+BM25 │
└───────┬───────┘  └───────┬───────────────┘
        │                  │
┌───────▼──────────────────▼───────────────┐
│  core/  基础设施                          │
│  DB(SQLAlchemy) / Redis缓存 / Chroma向量库│
│  LLM客户端(OpenAI兼容) / Embedding / 限流  │
└──────────────────────────────────────────┘
```

## 2. Agent 工作流（LangGraph）

状态定义见 `agent/graph/state.py`。图为有向无环图：

- **intent**：`agent/intent.py` 分层识别（规则 → LLM few-shot）。
- **retrieval**：`rag/retrieval/retriever.py` 多路检索，问候/转人工/投诉跳过。
- **tool_call**：`agent/graph/nodes/tool_call.py`（薄节点）→ 转人工判定与订单/退款工具调用逻辑在 `agent/dispatch.py`。
- **response**：`agent/graph/nodes/response.py` 流式生成（async generator，`stream_mode="custom"` 逐 token 输出）；缓存/兜底判定与消息构建在 `agent/generation.py`。

### 流式输出机制

`response` 节点是异步生成器：`yield` 每个 LLM token 作为 custom 事件；`return` 返回状态增量。调用方（`api/routes/chat.py`）用 `graph.astream(state, stream_mode=["custom","updates"])` 同时消费 token 与最终状态，将 token 以 SSE 转发，最终状态用于落库。

### 高频问答缓存

缓存键 `qa:{intent}:{归一化输入}`（仅对退款/售后/发票/优惠券/会员/报修等不涉个人数据的意图缓存）。命中时直接回放缓存文本，跳过 LLM，显著降低高并发下的推理压力。

## 3. RAG 引擎

```
文档 → parser.py（PDF/Word/Markdown/TXT）→ chunker.py（行业分块）→ pipeline.py（幂等入库）
                                                                       ↓
检索：query → vector_store.query（Chroma 余弦）┐
             → BM25Index（中文双字切分）          ├→ RRF 融合 → 重排 → top_k
                                                                       ↓
                                                → response 节点拼进 Prompt
```

### 行业分块规则（chunker.py）

1. 按 Markdown 标题层级切分章节，保留标题链。
2. 「问-答」配对整段保留，不拆散（`Q/A` 或以问号结尾）。
3. 短文本、口语化片段贪心合并，不做硬切。
4. 相邻块保留 overlap 重叠窗口，提升召回。

### BM25 中文切分

`tokenize()` 将连续中文按**双字切分**（如「退款流程」→「退款」「款流」「流程」），英文数字保留整词，无外部分词依赖。

## 4. 记忆体系

| 记忆 | 载体 | 作用 |
| --- | --- | --- |
| 短期会话记忆 | Redis（降级内存）key=`chat:hist:{session_id}` | 滑窗保留最近 N 轮，供多轮上下文 |
| 会话元信息 | Redis key=`chat:meta:{session_id}` | 未解决轮数、意图序列（歧义消解用） |
| 长期画像 | DB 聚合 | 用户意图分布、咨询主题，供个性化与运营 |
| 持久化 | conversation/message 表 | 审计、报表、会话回放 |

双写冗余：实时上下文走 Redis；Redis 缺失时从 message 表回退重建。

## 5. 分流与归档

`tool_call` 节点按四条规则触发转人工，调用 `human_tool` 创建 `Ticket`（含完整对话记录、问题摘要、意图、置信度），并在会话上标记 `transferred`。工单在运营后台可指派、结单、标记已解决。

每日报表 `services/report.py` 聚合：问题总量/解决/未解决/转人工/高频问题/意图分布/平均响应/缓存命中，支持脚本与后台定时生成。

## 6. 高并发设计

- 无状态 API + SQLAlchemy 连接池 + 多 worker（uvicorn `--workers N`）。
- Redis 缓存高频问答；BM25 索引进程内惰性构建，入库后失效重建。
- IP 限流（Redis INCR+EXPIRE，窗口自动滑动；降级内存）。
- 检索/生成超时控制；SSE 流式减少首字延迟。
- 生产建议：PostgreSQL + Redis 双依赖、Nginx 托管静态页、反向代理挂载 `/api`。

## 7. 关键依赖
